# 10-03: Deploy

**Phase:** 10 — Delivery
**Tipo:** DevOps

## Context

La app corre local (Django :8000 + Vite :5173). Para la demo puede correr local o deployarse.
Evaluar opciones según el constraint de $0.

## Opciones

### Opción A: Demo local (más simple, $0)
- Correr `python manage.py runserver` + `npm run dev`
- Usar `seed_demo` para datos
- Pro: sin config de deploy. Contra: requiere laptop en la presentación.

### Opción B: Deploy gratuito
- **Frontend:** Vercel o Netlify (build de Vite)
- **Backend:** Render o Railway (Django + SQLite/PostgreSQL)
- Configurar `CORS_ALLOWED_ORIGINS` con la URL del frontend
- Configurar `VITE_API_URL` con la URL del backend
- Pro: URL pública compartible. Contra: más setup, SQLite efímero en free tier.

## Task Breakdown
- [ ] T1: Decidir Opción A vs B (consultar con el equipo)
- [ ] T2: Si B — deploy del frontend (Vercel/Netlify)
- [ ] T3: Si B — deploy del backend (Render/Railway) con PostgreSQL
- [ ] T4: Si B — configurar CORS y VITE_API_URL
- [ ] T5: Verificar el flujo end-to-end en el entorno deployado

## Verification
- La app es accesible (local o URL pública)
- El flujo de demo funciona en el entorno final

## Notes
- Si se deploya, PostgreSQL es necesario (SQLite no persiste en free tier de Render).
- `DEBUG=False` en producción, `SECRET_KEY` real, `ALLOWED_HOSTS` correcto.
- El email backend es console-only — password reset no funcionará en producción real (aceptable para demo).
